# Native PAPER persistence

New Room database `local-financial-authority-v1.db` is separate from the existing response cache and remote database. Version1 creates two tables: accounts with immutable encrypted genesis/configuration plus a revision/head checkpoint; events with account/sequence primary key, unique account/event ID and account foreign key. Future schema changes require explicit Room migrations; no destructive migration or old-cache reset is enabled. Account reset means a new UUID, not deletion.

Each append runs in one database transaction: reconcile the entire bounded journal, check idempotency and expected revision, run risk/simulation, encrypt event+result, insert event and advance head with compare-and-swap. The source of truth is the immutable genesis and financial commands, not cached totals. Commands record approvals/rejections, order identity, bar/fill inputs and post-state. For this single-market scope, positions, outstanding orders and fills are reconstructed from those events rather than independently writable totals/tables. Rejected requests that cannot be validated throw and append nothing. A valid risk rejection is a durable event.

AES-GCM uses a separate Android Keystore key. Authenticated associated data binds the header to account ID and each event to account/sequence. SHA-256 links plaintext canonical event records and the genesis; replay checks sequence, uniqueness, head/revision and recomputed financial results. Payload reads are bounded; maximum10,000 events per experiment. This intentionally prioritizes correctness over throughput: full replay per append is unsuitable for unbounded high-frequency research, and no such throughput is claimed.

The instrumentation harness verifies creation, partial fill, close/open of database across an actual force-stop, exact reconstruction, optimistic-revision failure, conflicting/exact idempotency, concurrent writer exclusion and deliberate ciphertext corruption rejection. Tests only corrupt their disposable fixture journal.

Security limits: account IDs/revisions remain visible metadata. Device-key loss prevents decryption and is not silently repaired with new balances. GCM/hash chains detect modified/reordered events but do not prevent rollback to an entire older valid database snapshot. Rooted-device resistance, hardware rollback protection and portable authenticated export/restore remain unqualified. This device-bound store is not a portable backup format. Biometric app gating is not implemented by the ledger. Financial data is excluded by the existing app backup policy; production release remains blocked on broader security/device acceptance.
